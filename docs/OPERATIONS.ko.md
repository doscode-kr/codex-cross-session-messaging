# 업데이트와 진단

[English](OPERATIONS.md)

## 업데이트 전 Codex 호환성 확인

이 릴리스는 실험판입니다.
기록된 CI 검증은 Windows와 macOS의 Node.js 20과 22에서 Codex CLI 0.161.0을 사용했습니다.
검증 기록은 검사한 commit과 해당 결과를 명시합니다.
이전 Windows 기록에는 Codex 0.159.3 공유 데몬도 포함됩니다.
해당 기록은 다른 Codex 버전을 검증하지 않았습니다.
플러그인은 Codex 연결 시 `experimentalApi`를 활성화합니다.
통신 규약 변경은 세션 조회와 직접 입력에 영향을 줄 수 있습니다.
사용자는 [검증 기록](VERIFICATION.ko.md)에서 근거와 한계를 확인합니다.

1. 사용자는 `codex --version`으로 CLI 버전을 읽습니다.
2. 사용자는 해당 버전을 검증 기록과 비교합니다.
3. 사용자는 `npm run doctor`로 데몬 접근과 세션 목록을 확인합니다.

진단 성공은 메시지 전달을 증명하지 않습니다.
진단 성공은 작업 완료를 증명하지 않습니다.
사용자는 검증 기록의 격리 통합 절차로 검증하지 않은 버전을 점검할 수 있습니다.
격리 통합 검증은 모형 서버를 사용합니다.
격리 통합 검증은 실제 모델의 동료 요청 이해를 증명하지 않습니다.
격리 통합 검증은 실제 모델의 작업 완료를 증명하지 않습니다.
설치 스크립트는 운영 중인 Codex 데몬을 업데이트하지 않습니다.
설치 스크립트는 운영 중인 Codex 데몬을 재시작하지 않습니다.

## 같은 원본 폴더에서 업데이트

1. 사용자는 현재 릴리스 태그나 commit을 기록합니다.
2. 사용자는 등록된 원본 폴더에서 새 릴리스를 받습니다.
3. 사용자는 [변경 기록](../CHANGELOG.ko.md)을 읽습니다.
4. 사용자는 신청한 원래 세션에서 남은 대기 알림을 취소합니다.
5. 사용자는 기존 플러그인을 읽은 세션을 닫습니다.
6. 사용자는 외부 셸에서 메시지 브로커를 종료합니다.

   ```text
   node plugins/cross-session/src/cli.mjs broker-stop
   ```

7. 사용자는 설치 명령을 확인합니다.

   ```text
   node scripts/install.mjs --dry-run
   ```

8. 사용자는 기존 플러그인 캐시를 삭제합니다.

   ```text
   codex plugin remove cross-session@cross-session-local
   ```

9. 사용자는 새 원본을 설치합니다.

   ```text
   npm run install:global
   ```

10. 사용자는 새 Codex CLI 세션을 엽니다.
11. 사용자는 `/hooks`에서 새 훅을 검토합니다.
12. 사용자는 `npm run doctor`를 실행합니다.

원본 폴더와 설치된 캐시는 별도 위치입니다.
원본 변경만으로 캐시 업데이트를 확인할 수 없습니다.
이 절차는 메시지 데이터를 유지합니다.
설치 스크립트는 운영 데몬을 재시작하지 않습니다.
브로커 종료 후 다음 플러그인 호출은 새 브로커 코드를 읽습니다.
`broker-stop`의 `BROKER_OFFLINE`은 해당 메시지 폴더의 브로커가 실행 중이 아니라는 뜻입니다.
종료 훅이 브로커를 다시 시작할 수 있으므로 사용자는 브로커 종료 전에 플러그인 세션을 닫습니다.

## 원본 폴더 변경

마켓플레이스 이름이 다른 원본에 등록되어 있을 수 있습니다.
이 경우 설치 스크립트는 오류를 반환합니다.

1. 사용자는 `codex plugin list --json`으로 설치 목록을 읽습니다.
2. 사용자는 다른 설치된 플러그인의 `cross-session-local` 사용 여부를 확인합니다.
3. 사용자는 신청한 원래 세션에서 남은 대기 알림을 취소합니다.
4. 사용자는 기존 플러그인을 읽은 세션을 닫습니다.
5. 사용자는 외부 셸에서 `node plugins/cross-session/src/cli.mjs broker-stop`을 실행합니다.
6. 사용자는 `codex plugin remove cross-session@cross-session-local`을 실행합니다.
7. 다른 설치된 플러그인이 사용하지 않으면 사용자는 `codex plugin marketplace remove cross-session-local`을 실행합니다.
8. 사용자는 새 원본 폴더에서 `npm run install:global`을 실행합니다.
9. 사용자는 새 Codex CLI 세션을 엽니다.
10. 사용자는 `/hooks`에서 훅을 검토합니다.

다른 설치된 플러그인이 해당 마켓플레이스를 사용하면 사용자는 2단계 후 이 절차를 중단합니다.
사용자는 해당 등록과 원본을 유지합니다.
기존 등록을 유지하며 새 원본이 필요하면 사용자는 별도 `CODEX_HOME`을 사용합니다.

사용자는 각 명령에 같은 `CODEX_HOME`을 사용합니다.
사용자는 새 설치를 확인할 때까지 기존 원본을 유지합니다.
이전 상태가 필요하면 사용자는 기록한 릴리스를 다시 설치합니다.

## 사용할 수 없는 원본 폴더 복구

등록된 원본 폴더를 옮기거나 삭제하면 Codex의 플러그인 목록 조회가 실패할 수 있습니다.
설치된 캐시는 남아 있을 수 있습니다.
설치 스크립트와 삭제 스크립트는 목록 조회가 실패하면 멈춥니다.
설치 기록의 원본 경로를 사용할 수 없으면 오류에는 해당 경로와 Codex 설정 폴더가 표시됩니다.
오류에는 원래 Codex 오류도 표시됩니다.
설치 기록은 진단 정보만 제공합니다.
설치 기록은 현재 마켓플레이스 소유자를 확인하지 않습니다.
설치 기록은 등록 삭제를 허용하지 않습니다.
기록된 경로를 사용할 수 없다는 사실만으로 실패 원인을 확정할 수 없습니다.
사용할 수 있는 기록이 없으면 스크립트는 원래 오류를 유지합니다.

1. 사용자는 원래 Codex 오류를 읽습니다.
2. 설치 기록이 있으면 사용자는 `<CODEX_HOME>/.cross-session-install.json`의 `sourceRoot`를 확인합니다.
3. 사용자는 보관한 사본이나 릴리스로 원래 원본 저장소를 기록된 경로에 복원합니다.
4. 사용자는 같은 `CODEX_HOME`으로 `codex plugin marketplace list --json`을 실행합니다.
5. 사용자는 같은 `CODEX_HOME`으로 `codex plugin list --json`을 실행합니다.
6. 사용자는 다른 설치된 플러그인의 `cross-session-local` 사용 여부를 확인합니다.
7. 원본 이동이 필요하면 사용자는 위의 원본 폴더 변경 절차를 따릅니다.

목록 조회가 계속 실패하면 사용자는 복원한 원본을 유지합니다.
사용자는 원래 오류를 조사합니다.
설치 기록이 없으면 사용자는 보관한 설치 자료에서 등록 경로를 찾습니다.
사용자는 오류를 우회하기 위해 빈 원본 폴더를 만들지 않습니다.
사용자는 오류를 우회하기 위해 설치 기록을 변경하지 않습니다.
사용자는 이 실패를 복구하기 위해 Codex 설정을 삭제하지 않습니다.
사용자는 플러그인 등록과 캐시와 메시지 데이터를 삭제하지 않습니다.
다른 설치된 플러그인이 마켓플레이스를 사용하면 사용자는 해당 등록과 원본을 유지합니다.
기존 등록을 안전하게 변경할 수 없으면 사용자는 별도 `CODEX_HOME`을 사용합니다.

플러그인 변경이나 삭제 전에 사용자는 신청한 원래 세션에서 대기 알림을 취소합니다.
브로커 종료 전에 사용자는 기존 플러그인을 읽은 세션을 닫습니다.
기존 원본을 사용할 수 없으면 사용자는 복원한 원본이나 새 원본에서 `node plugins/cross-session/src/cli.mjs broker-stop`을 실행할 수 있습니다.
사용자는 기존 브로커가 사용한 `CODEX_HOME`과 `CROSS_SESSION_HOME` 설정을 사용합니다.
종료 명령은 마켓플레이스 등록을 복구하지 않습니다.
종료 명령은 Codex 데몬을 재시작하지 않습니다.
종료가 실패하면 사용자는 메시지 데이터를 유지합니다.
사용자는 [삭제 안내](UNINSTALL.ko.md)를 따릅니다.
복원 후 사용자는 같은 `--home` 폴더로 설치 스크립트나 삭제 스크립트를 다시 실행할 수 있습니다.
설치 스크립트는 의존성 설치 전에 플러그인 목록을 조회합니다.
모의 실행은 예정된 명령만 표시합니다.
모의 실행은 Codex 플러그인 목록을 조회하지 않습니다.
모의 실행은 원본 복구 성공을 확인하지 않습니다.

## journal 메모리와 증가

브로커는 완성된 journal 줄을 하나씩 복원합니다.
브로커는 메시지 정보를 메모리에 보관합니다.
응답에 메시지 본문이 필요하면 브로커는 `events.jsonl`에서 본문을 읽습니다.
브로커는 본문 캐시를 보관하지 않습니다.
기존 메시지와 완성된 이벤트 이력은 유지합니다.
같은 정보를 다시 기록하면 새 이벤트를 추가하지 않습니다.
세션 시각이나 읽음 확인 시각이 바뀌면 새 이벤트를 추가합니다.
따라서 반복 기록은 모든 시도의 완전한 감사 이력이 아닙니다.

완성된 이벤트가 잘못됐으면 브로커는 시작을 중단합니다.
브로커는 앞의 모든 완성된 이벤트를 확인한 뒤에만 마지막 미완성 줄을 제거합니다.
본문 읽기가 실패하면 브로커는 이후 쓰기를 중단합니다.
사용자는 journal을 보존합니다.
사용자는 저장 장치 문제를 해결한 뒤 브로커를 다시 시작합니다.

브로커는 journal을 자동 압축하지 않습니다.
브로커는 메시지를 자동 삭제하지 않습니다.
저장된 이벤트가 늘어나면 디스크 사용량과 재시작 시간이 늘어납니다.
메시지가 늘어나면 메시지 정보를 보관하는 메모리도 늘어납니다.
아주 큰 이벤트 하나도 많은 메모리를 사용할 수 있습니다.
본문을 필요할 때 읽으므로 메시지 조회의 디스크 읽기 횟수가 늘어날 수 있습니다.
명시적인 데이터 삭제 절차는 [삭제 안내](UNINSTALL.ko.md)를 사용합니다.

## broker 응답 오류

`BROKER_TIMEOUT`은 client가 완전한 응답을 받지 못했다는 뜻이다.
응답 본문을 읽는 중 발생한 timeout과 확인된 연결 실패도 여기에 포함된다.
`BROKER_RESPONSE_INVALID`는 응답의 JSON이나 구조가 잘못됐다는 뜻이다.
두 오류 모두 broker의 요청 처리 여부를 확인하지 못한다.
client는 이 오류 뒤 메시지 요청, hook 요청, 종료 요청을 자동 재전송하지 않는다.
client는 연결과 응답 본문에 같은 timeout을 적용한다.
오류 정보는 요청 경로와 불명확한 처리 결과를 표시한다.
오류 정보는 잘못된 응답 본문이나 인증 token을 포함하지 않는다.

1. 다른 메시지를 보내기 전에 보낸 메시지 기록을 읽는다.
2. 종료를 다시 요청하기 전에 broker 상태를 확인한다.
3. 처리 결과가 불명확하면 메시지 journal을 보존한다.

잘못된 health 응답은 broker 자동 시작의 조건이 아니다.
유효한 broker 거부 응답은 원래 오류 코드와 메시지를 유지한다.
성공 응답은 JSON 객체여야 한다.
health 응답은 요청한 메시지 디렉터리를 식별해야 한다.
종료 응답은 `stopped: true`를 확인해야 한다.

## 진단

| 문제 | 확인할 항목 |
|---|---|
| Codex 실행 파일 없음 | `CROSS_SESSION_CODEX_BIN`에 실행 파일 절대 경로를 지정합니다. |
| 공유 데몬 없음 | `--no-daemon` 없이 일반 Codex CLI 세션을 시작합니다. |
| 세션 목록 누락 | 독립 루트 세션이 데몬에 적재되었는지 확인합니다. |
| 이름이나 프로젝트 정보 없음 | 훅 신뢰를 확인합니다. 세션 이름을 등록합니다. |
| 전달 결과 불확실 | 재전송 전에 발신 기록을 읽습니다. |
| 브로커 종료 거부 | 현재 세션의 대기 알림을 취소합니다. |
| 마켓플레이스 원본 충돌 | 위의 원본 폴더 변경 절차를 따릅니다. |
| 원본 폴더 이동 후 플러그인 목록 조회 실패 | 위의 복구 절차로 기록된 원본 경로를 복원합니다. |

`npm run doctor`는 데몬과 세션 목록을 읽습니다.
출력에는 세션 ID와 프로젝트 경로가 포함될 수 있습니다.
사용자는 출력을 공유하기 전에 개인정보를 제거합니다.

브로커 종료 명령은 `node plugins/cross-session/src/cli.mjs broker-stop`입니다.
이 명령은 Codex 데몬을 종료하지 않습니다.
대기 알림 신청이 남으면 브로커는 종료를 거부합니다.
삭제와 데이터 정리는 [삭제 안내](UNINSTALL.ko.md)를 따릅니다.

`broker-stop`이 `DELIVERIES_ACTIVE`를 반환하면 사용자는 다음 절차를 따릅니다.

1. 사용자는 진행 중인 메시지 전달 응답을 기다립니다.
2. 사용자는 `broker-stop`을 다시 실행합니다.

`BROKER_STOPPING`을 반환한 요청은 수락되지 않았습니다.
이 오류는 이전에 수락된 전달 결과를 변경하지 않습니다.
이 오류는 이전의 불확실한 전달 결과를 변경하지 않습니다.
