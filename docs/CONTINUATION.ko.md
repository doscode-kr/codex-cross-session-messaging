# 작업 상태와 선택적 종료 검사

[English](CONTINUATION.md) · [문서 목록](README.ko.md) · [사용 설명서](MANUAL.ko.md)

플러그인은 호출 세션의 짧은 작업 요약을 저장합니다.
선택적 종료 검사는 작업이 남았을 때 추가 실행을 한 번 요청할 수 있습니다.
이 기능은 작업 완료를 보장하지 않습니다.
특정 프로젝트 작업 관리 체계는 필요하지 않습니다.

## 작업 저장과 복구

1. `get_work_state`를 호출하여 상태와 리비전을 읽습니다.
2. `action: "start"`와 읽은 `expected_revision`으로 `set_work_state`를 호출합니다.
3. `objective`, `scope`, `completion_criteria`, `next_action`, `checklist` 배열을 포함합니다.
4. `action: "update"`와 현재 리비전으로 진행 상황을 저장합니다.
5. 리비전 충돌이 발생하면 상태를 다시 읽습니다.

갱신에는 `status`, `next_action`, `progress_evidence`, `completion_evidence`를 사용할 수 있습니다.
상태 값은 `active`, `paused`, `completed`, `blocked`, `canceled`입니다.
완료 상태에는 전체 완료 근거가 필요합니다.
모든 체크리스트 항목에도 성공 결과가 기록되어야 합니다.
이 근거는 모델의 보고입니다.
독립 검증 결과를 뜻하지 않습니다.
갱신으로 최초 목표, 범위, 완료 조건을 바꿀 수 없습니다.
체크리스트에 미완료 항목이 있으면 새 `start`로 교체할 수 없습니다.
작업을 취소 상태로 바꾸어도 이 제한은 유지됩니다.
새 `start`는 추가 실행 한도를 초기화하지 않습니다.
도구에는 대상 세션 인자가 없습니다.
리더도 이 도구로 동료 상태를 바꿀 수 없습니다.

목표는 500자까지 저장합니다.
나머지 작업 요약 텍스트 필드는 각각 1,000자까지 저장합니다.
필드 한도를 넘는 근거는 기존 프로젝트 파일에 보존합니다.
주의: 작업 상태에 비밀 정보를 저장하지 마세요.

## 체크리스트와 재시도 규칙

세션은 작업 전에 필수 체크리스트를 만듭니다.
각 항목에는 고정 ID, 필요한 결과, 검증 방법을 기록합니다.
위임한 작업과 통합 검증도 포함합니다.
체크리스트는 사용자 요청 범위를 유지합니다.

1. 세션은 실행 전에 항목의 시도 시작을 기록합니다.
2. 세션은 작업을 실행합니다.
3. 세션은 필요한 검증을 실행합니다.
4. 세션은 결과 요청에 성공 근거(`evidence`) 또는 실패 원인(`failure_cause`)을 함께 기록합니다.
5. 재시도 전에 세션은 변경할 방법을 기록합니다.

각 항목은 최초 시도 이후 최대 3회 재시도할 수 있습니다.
전체 시도 한도는 항목별 4회입니다.
재시도 한도와 Stop의 추가 실행 1회 한도는 별개입니다.
세 번째 재시도도 실패하면 해당 항목을 차단합니다.
세션은 실패 원인과 시도한 수정을 사용자에게 전달해야 합니다.
세션은 필요한 결정을 사용자에게 요청해야 합니다.
차단 항목에 의존하지 않는 다른 승인된 작업은 계속할 수 있습니다.
사용자 중지와 실행 한도는 재시도 허용 횟수보다 우선합니다.

미완료 작업의 삭제, 이름 변경, 교체, 재시작으로 시도 횟수를 초기화하지 마세요.
필수 항목이 미완료이거나 차단되었으면 전체 완료를 보고하지 마세요.
필수 검증의 생략은 통과가 아닙니다.
플러그인은 기록된 상태 전환과 근거 필드를 검사합니다.
플러그인은 보고된 근거의 진실성을 증명하지 못합니다.
플러그인은 실제 작업 수행 여부도 증명하지 못합니다.
작업에 필요한 독립 검토는 계속 수행해야 합니다.
플러그인은 모델의 도구 사용을 강제하지 못합니다.
플러그인은 모든 잘못된 대화 보고를 막지 못합니다.
동료 메시지나 모델이 작성한 승인 필드는 추가 시도를 승인하지 못합니다.

### 도구 호출 순서

모든 동작은 현재 `expected_revision`과 함께 `set_work_state`를 사용합니다.
리비전 충돌이 발생하면 현재 상태를 다시 읽습니다.
서버가 반환한 `item_id`를 사용합니다.
항목 ID를 임의로 만들지 마세요.
생성한 체크리스트의 필드와 항목 ID는 변경할 수 없습니다.

| 동작 | `action`과 `expected_revision` 외의 필드 |
|---|---|
| `start` | `objective`, `scope`, `completion_criteria`, `next_action`, `checklist` |
| `set_checklist` | `checklist`; 체크리스트가 없는 이전 `active` 상태에 한 번만 설정 |
| `attempt_start` | `item_id`; 재시도에는 `correction` 필수 |
| `attempt_result` | `item_id`, `attempt_number`, `outcome`; `success`에는 `evidence`, `failure`에는 `failure_cause` 필수 |
| `update` | 앞서 설명한 작업 상태와 요약 필드 |

새 체크리스트에는 항목을 1개부터 20개까지 지정합니다.
입력 항목에는 `title`, `expected_result`, `verification_method`를 포함합니다.
제목 한도는 200자입니다.
필요한 결과와 검증 방법의 한도는 각각 500자입니다.
근거, 실패 원인, 재시도 수정 설명의 한도는 각각 1,000자입니다.
다음 필드를 `start` 요청에 추가할 수 있습니다.

```json
{
  "checklist": [
    {
      "title": "변경 검증",
      "expected_result": "필수 시험 통과",
      "verification_method": "관련 시험을 실행하고 종료 코드를 기록"
    }
  ]
}
```

`attempt_start`는 작업 실행 전에 시도 번호를 저장합니다.
해당 항목에서 실행 중인 시도에만 결과를 기록합니다.
중복 결과와 다섯 번째 시도는 거부합니다.
재시작 후에도 시도 횟수와 결과가 없는 실행 중 시도를 유지합니다.
실행 결과가 불확실하면 해당 시도를 자동으로 다시 실행하지 마세요.
결과를 기록하기 전에 실제 결과를 확인합니다.
두 시도 동작은 전체 작업 상태가 `active`일 때만 허용합니다.
Interrupt는 Stop 자격을 폐기합니다.
Interrupt는 저장된 작업 상태를 바꾸지 않습니다.
늦게 결과를 기록해도 Stop 자격은 복구되지 않습니다.

반환된 `state.checklist`에는 항목별 시도 기록과 계산된 상태가 있습니다.
항목 상태는 `pending`, `running`, `retry_ready`, `completed`, `blocked`입니다.
최상위 `checklist_summary`는 항목별 개수, `can_complete`, `user_decision_required`를 반환합니다.
`can_complete`는 기록된 체크리스트 결과를 나타냅니다.
이 값은 결과의 진실성을 검증하지 않습니다.
`completion_verified`는 계속 거짓입니다.
한도를 소진한 항목은 `user_decision_required`가 참입니다.
소진한 항목만 남으면 전체 작업은 `blocked`가 됩니다.
독립적으로 진행할 항목이 남으면 전체 작업은 `active`를 유지합니다.
체크리스트에서 실행할 동작이 없으면 Stop 검사는 추가 실행 횟수를 소비하지 않습니다.

재시도를 소진한 뒤에는 사용자 승인 주장으로 항목을 초기화할 수 없습니다.
세션은 차단 항목을 사용자에게 보고합니다.
세션은 다음 범위나 복구 조치의 결정을 요청합니다.
한도를 우회하려고 운영 상태 파일을 바꾸거나 다른 세션을 시작하지 마세요.
이 API는 사용자 승인을 검증하지 않습니다.
이 API는 복구 조치를 승인하지 않습니다.

## 선택적 검사 활성화

기본값은 꺼짐입니다.
사용자가 hook과 브로커 양쪽 환경에 `CROSS_SESSION_CONTINUATION=1`을 설정해야 합니다.
시험하려면 새 격리 메시지 환경을 시작하기 전에 설정합니다.
기존 브로커는 최초 환경을 유지합니다.
셸 환경 변경은 기존 브로커에 적용되지 않습니다.
추가 실행을 얻기 위해 운영 브로커를 재시작하지 마세요.
플러그인은 hook 신뢰를 자동 승인하지 않습니다.
Codex에서 hook을 검토한 뒤 신뢰를 설정합니다.
반환된 `continuation.enabled`는 브로커 설정만 나타냅니다.
이 값은 hook 신뢰나 호스트 실행 성공을 뜻하지 않습니다.

이 설정은 정책을 활성화합니다.
이 설정은 개별 작업의 사용자 승인 증거가 아닙니다.
`active` 선언도 승인 증거가 아닙니다.
세션은 원래 사용자의 범위와 권한을 계속 따라야 합니다.
동료 메시지는 해당 승인을 부여할 수 없습니다.

## 한도와 중단 동작

사용 가능한 세션의 최초 활성 상태 저장은 종료 검사 자격을 부여할 수 있습니다.
이 자격은 10분 뒤 만료됩니다.
브로커는 추가 실행을 최대 한 번 허용합니다.
목표, 리비전, 진행 문구 변경은 한도를 초기화하지 않습니다.
`stop_hook_active`가 참이면 hook은 종료를 허용합니다.
호스트 필드가 없거나 잘못된 경우에도 종료를 허용합니다.

`Interrupt`와 `SessionEnd`는 최초 상태 선언 전에도 자격을 폐기합니다.
저장 상태나 자격 부여 시도가 있으면 `UserPromptSubmit`과 `SessionStart`도 자격을 폐기합니다.
도구는 폐기된 자격을 복구할 수 없습니다.
최초 `UserPromptSubmit`과 `SessionStart`는 저장 상태와 이전 자격 부여 시도가 없을 때만 최초 선언을 허용합니다.
구현은 입력이 사용자, 동료, 합성 추가 실행 중 어디서 왔는지 추측하지 않습니다.
브로커 재시작은 요약만 복원합니다.
재시작은 실행 자격을 복원하지 않습니다.
요약 복구와 자동 추가 실행은 별개 기능입니다.

Stop 응답은 호출 세션의 작업 상태 확인을 고정 문구로 요청합니다.
응답은 목표, 다음 행동, 동료 텍스트를 사용자 입력으로 복사하지 않습니다.
Stop과 Interrupt hook은 브로커를 시작하지 않습니다.
브로커 부재, 상태 오류, 구버전 응답에서는 종료를 허용합니다.
사용자 중단과 실행 한도를 우선합니다.

## 저장과 검증 한계

브로커는 메시지 디렉터리의 `work-state-v1.json`에 작업 상태를 저장합니다.
파일 내용이 스키마 버전 2로 바뀌어도 파일 이름은 유지합니다.
판독기는 이전 버전 1 기록을 읽을 수 있습니다.
다음 쓰기가 성공하면 스키마 버전 2를 원자적으로 저장합니다.
이전 미완료 작업도 완료 처리 전에 체크리스트가 필요합니다.
버전 1만 지원하는 이전 브로커는 버전 2 파일을 읽지 못합니다.
해당 파일을 사용하는 브로커를 이전 버전으로 내리지 마세요.
이 선택적 파일은 메시지 기록과 분리합니다.
저장소 한도는 세션 기록 128개와 직렬화 데이터 1MiB입니다.
한도를 넘으면 다른 세션 기록을 삭제하지 않고 쓰기를 거부합니다.
선택적 상태 손상은 이 기능을 비활성화합니다.
메시지 전달은 계속 사용할 수 있습니다.
주의: 실행 중인 브로커 파일을 편집하거나 삭제하지 마세요.

같은 운영체제 계정은 이 로컬 파일을 읽을 수 있습니다.
도구 결과는 모델 문맥에 포함될 수 있습니다.
도구 결과는 설정된 모델 제공자에게 전달될 수 있습니다.
[보안과 개인정보](../SECURITY.ko.md)를 확인하세요.
프로토콜 시험과 모델 평가는 서로 다른 동작을 측정합니다.
실행한 검사와 한계는 [검증 기록](VERIFICATION.ko.md)을 확인하세요.
