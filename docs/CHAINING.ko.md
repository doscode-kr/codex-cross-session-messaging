# 다른 세션에서 작업 이어 하기

[English](CHAINING.md) · [문서 목록](README.ko.md) · [작업 상태](CONTINUATION.ko.md)

세션 체이닝은 새 Codex 세션에 이전 세션의 인계 내용을 전달합니다.
세션을 다시 열거나 대화를 압축한 뒤에도 저장한 내용을 복원합니다.
두 세션은 같은 컴퓨터의 같은 메시지 저장 폴더를 사용해야 합니다.

사용자는 작업에 체인 ID를 붙입니다.
연결 정보는 전체 세션 UUID 하나를 체인 하나에 연결합니다.
체크포인트는 특정 시점의 인계 내용을 담은 파일입니다.
플러그인은 한 번 저장한 체크포인트를 바꾸지 않습니다.
새 세션을 연결할 때 원본 체크포인트를 고정합니다.
원본 세션이 나중에 저장해도 이 고정값은 바뀌지 않습니다.
새 세션이 자체 체크포인트를 저장한 뒤에는 그 세션의 최근 체크포인트를 복원합니다.

## 원본 세션 준비

1. [업데이트 안내](OPERATIONS.ko.md)에 따라 새 플러그인을 설치합니다.
2. Codex `/hooks`에서 플러그인 hook을 검토합니다.
3. 사용할 hook을 신뢰하도록 승인합니다.
4. 새 플러그인을 사용하는 세션을 엽니다.
5. `link_chain`에 `{"chain_id":"release-fix"}`를 전달합니다.
6. [작업 상태 안내](CONTINUATION.ko.md)에 따라 `set_work_state`로 인계를 작성합니다.
7. 턴을 끝내 Stop hook이 체크포인트를 저장하게 합니다.
8. `get_chain`으로 전체 세션 UUID와 체크포인트 ID를 읽습니다.

체인 ID에는 ASCII 영문, 숫자, 마침표, 밑줄, 붙임표를 쓸 수 있습니다.
길이는 1~80자입니다.
세션과 체크포인트 ID에는 소문자로 된 전체 UUID를 사용합니다.
이름, UUID 앞자리, 브랜치, 최신 세션으로 원본을 고를 수는 없습니다.

구조화 인계는 기존 작업 상태 파일에서 읽습니다.
결정과 근거 파일의 위치는 `progress_evidence`에 기록합니다.
남은 작업은 체크리스트와 `next_action`에 기록합니다.
작업 단위가 끝나거나 다음 행동이 바뀌면 이 내용을 갱신합니다.
자동 대화 기록만으로는 이 내용을 충분히 전달할 수 없습니다.
작업 상태가 없으면 복원 내용에 자동 기록만 있다는 표시를 넣습니다.

## Launch 지원 상태

현재 `chain launch`는 `CHAINING_LAUNCH_UNSUPPORTED`를 반환합니다.
티켓을 만들거나 프로세스를 시작하지 않습니다.
공유 Codex 데몬은 새 CLI 프로세스의 환경 변수를 받지 않습니다.
따라서 자식 환경에만 넣은 티켓은 SessionStart에 도달하지 않습니다.
Windows의 Codex 0.164.0 시험에서 이 실패를 확인했습니다.
0.161.0과 0.164.0에서는 세션별 설정으로 티켓을 전달하면 별도 서버를 사용했습니다.
그 서버의 세션은 이 플러그인이 사용하는 공유 데몬에서 조회되지 않았습니다.
`--codex-js` 절대 경로나 `--no-daemon`으로도 이 제한을 해결할 수 없습니다.

티켓 저장과 hook의 사용 검사는 구현했지만 지원 가능한 launch 전달 경로는 아직 없습니다.
검사는 `claimed`, `owner_resume`, `expired`, `consumed`, `mismatch`, `missing_ticket`, `invalid_ticket`을 구분합니다.
미사용 티켓의 기한은 10분입니다.
소유 세션은 기한 뒤에도 재개할 수 있습니다.
거부한 티켓으로는 인계를 주입하지 않습니다.
티켓은 첫 사용자를 소유자로 삼으며 상위 세션의 의도를 인증하지 않습니다.
티켓을 전역 설정이나 셸 프로필에 넣지 않습니다.

## 종료한 세션에 인계 복원

1. 인계를 받을 세션의 전체 UUID를 기록합니다.
2. 해당 세션을 완전히 종료합니다.
3. 다른 터미널에서 다음 명령을 실행합니다.
4. 정확한 UUID로 인계를 받을 세션을 다시 엽니다.

```text
node plugins/cross-session/src/cli.mjs chain link --session RECEIVING_UUID --chain-id release-fix --source-session-id SOURCE_UUID
```

두 자리표시자를 소문자 전체 UUID로 바꿉니다.
원본 세션에는 선택한 체인의 자체 체크포인트가 있어야 합니다.
다음 SessionStart가 고정한 인계를 복원합니다.
Codex는 첫 입력 때 SessionStart를 실행할 수 있습니다.
연결 명령 뒤에는 세션을 재개할 때까지 닫아 둡니다.

## 이미 열린 세션 연결

인계를 받을 세션에서 `link_chain`을 호출합니다.

```json
{"chain_id":"release-fix","source_session_id":"11111111-0000-4000-8000-000000000001"}
```

MCP 도구는 Codex가 제공한 정보에서 호출자의 UUID를 확인합니다.
모델이 호출자의 세션 ID를 인자로 지정할 수는 없습니다.
원본 세션에 자체 체크포인트가 없으면 `CHAINING_NO_CHECKPOINT`를 반환합니다.
CLI에서는 `chain link --session UUID --chain-id ID --source-session-id UUID`를 사용합니다.
CLI의 `--session`은 환경 변수 `CODEX_THREAD_ID`로 대신할 수 있습니다.
연결 호출은 현재 모델 문맥을 바꾸지 않습니다.
SessionStart가 원본 인계나 축소한 원본 참조를 출력할 때까지 연결은 `restore_pending` 상태를 유지합니다.
이때 저장 hook은 `awaiting_restore`를 반환하며 새 체크포인트로 원본을 가리지 않습니다.
같은 UUID의 세션을 다시 열면 인계를 받습니다.
출력 쓰기에 성공하면 hook이 확인 기록을 저장합니다.
확인 기록을 저장한 뒤에는 체크포인트 저장을 허용합니다.
이 확인은 호스트나 모델이 인계를 읽었다는 증거가 아닙니다.
확인 기록의 저장 전에 오류가 나면 다음 SessionStart가 원본 인계를 다시 출력할 수 있습니다.
확인 결과가 불확실하면 hook은 자동으로 다시 시도하지 않습니다.

## 연결 확인과 수정

1. `get_chain`으로 현재 연결 정보를 읽습니다.
2. `unlink_chain`에 `expected_chain_id`와 `expected_checkpoint_id`를 전달합니다.
3. 반환된 `tombstone.id`를 읽습니다.
4. `relink_chain`에 `tombstone_id`, 새 `chain_id`, 필요한 원본 UUID를 전달합니다.

체크포인트 비교값에는 먼저 `latest_checkpoint_id`를 사용합니다.
그 값이 없으면 `pinned_checkpoint_id`를 사용합니다.
둘 다 null이면 문자열 `none`을 사용합니다.
해제하는 동안 다른 저장이 끝나면 최근 체크포인트가 바뀔 수 있습니다.
`CHAINING_CONFLICT`가 나오면 현재 연결 정보를 다시 읽습니다.
해제 기록은 해당 UUID의 자동 재연결과 저장을 막습니다.
다시 연결하려면 정확한 해제 기록 ID가 필요합니다.
CLI의 `chain` 아래에도 `status`, `unlink`, `relink` 명령이 있습니다.
각 옵션은 `chain --help`에서 확인할 수 있습니다.

해제해도 모델에게 이미 전달한 문맥은 지워지지 않습니다.
잘못된 인계를 받았다면 새 세션을 사용합니다.
연결을 고칠 때는 명령을 사용합니다.
복구하려고 저장소 파일을 직접 지우지 않습니다.

## Hook과 진단

`Stop`, `PreCompact`, `SessionEnd`가 연결된 세션을 저장합니다.
Stop은 호스트가 제공한 마지막 어시스턴트 메시지도 저장합니다.
SessionEnd는 짧은 시간 안에 끝내야 하므로 기록 정리와 Git 명령을 실행하지 않습니다.
연결하지 않은 세션과 하위 에이전트는 체크포인트를 저장하지 않습니다.
hook 입력과 대화 기록의 UUID가 다르면 거부합니다.
큰 대화 파일에서는 앞부분의 신원과 뒷부분의 최근 사용자·어시스턴트 발화만 읽습니다.
도구 결과, 추론, system·developer 메시지는 담지 않습니다.
깨진 JSON 줄은 건너뛰지만 신원 확인은 생략하지 않습니다.

일반 세션의 SessionStart에는 `Cross-session chaining hook attached.`라는 줄이 붙습니다.
이어지는 상태는 `unbound`, `bound_no_notes`, `restored`, `rejected`, `unlinked`, `storage_error` 중 하나입니다.
Codex가 hook을 실행하지 않으면 부착 줄도 없습니다.
다음 읽기 전용 명령으로 설치된 hook과 저장소 사용량을 확인합니다.

```text
node plugins/cross-session/src/cli.mjs chain doctor
```

결과는 hook별 설정 여부, 활성 여부, 신뢰 상태를 보여줍니다.
진단은 Codex `hooks/list`의 결과를 읽습니다.
진단이 hook을 신뢰하도록 승인하지는 않습니다.
`ready`는 hook이 설정되고 활성화되어 있으며 신뢰받는다는 뜻입니다.
실제 실행 여부는 부착 줄과 체크포인트 상태로 확인합니다.
업데이트로 새 hook 이벤트를 추가하면 사용자가 다시 신뢰를 검토해야 합니다.
이번 변경은 `PreCompact`를 추가합니다.
기존 hook의 명령 문자열과 배열 위치는 유지합니다.

복원 내용에는 신뢰하지 않는 데이터라는 표시를 넣습니다.
구조화 인계도 이전 모델의 보고이며 독립 검증 결과는 아닙니다.
자동 기록에는 미확정 표시를 넣습니다.
이전 세션의 다음 행동은 현재 사용자 요청과 권한 안에서 검토할 제안입니다.
복원해도 작업 상태의 소유자나 Stop 추가 실행 자격은 바뀌지 않습니다.
새 세션을 열어 미완료 체크리스트의 시도 횟수를 초기화해서는 안 됩니다.

복원 내용에는 바이트 한도가 있습니다.
한도를 넘으면 자동 발화, Git 정보, 목록의 오래된 항목 순서로 줄입니다.
그래도 크면 긴 인계 문구를 체크포인트 식별 정보로 바꿉니다.
JSON 형식, 줄였다는 표시, 원본 파일 경로는 유지합니다.
크기를 줄이려고 디스크의 체크포인트를 바꾸지는 않습니다.

## 저장과 한도

메시지 저장 폴더 안에 `chaining-v1/state.json`과 `chaining-v1/checkpoints/`를 둡니다.
기본 폴더는 `$CODEX_HOME/cross-session`입니다.
`CODEX_HOME`이 없으면 `~/.codex/cross-session`을 사용합니다.
`CROSS_SESSION_HOME`은 다른 메시지 환경을 지정합니다.
체크포인트에는 기존 작업 상태의 특정 시점 복사본을 넣습니다.
쓰기 잠금으로 동시 저장이 서로 덮어쓰지 않게 합니다.
완성된 파일만 최종 경로에 보이도록 저장합니다.
동시 쓰기는 손상 없이 끝나거나 `CHAINING_BUSY`로 명시적으로 거부됩니다.
저장 도우미가 오래 걸리면 hook은 시간 한도 전에 도우미를 끝냅니다.
종료를 확인한 도우미의 잠금만 정확한 소유 정보로 해제합니다.
부모 프로세스도 중단되면 잠금이 남을 수 있습니다.
`chain doctor`의 `lock_present`가 남은 잠금을 보여줍니다.
잠금의 소유 상태를 해결하기 전까지 이후 쓰기는 막힙니다.
시간 초과만으로 저장 실패를 단정하거나 불확실한 쓰기를 자동으로 반복하지 않습니다.

| 한도 | 기본값 |
|---|---|
| 색인 파일 | 2 MiB |
| 체크포인트 하나 | 256 KiB |
| 체이닝 저장소 전체 | 64 MiB |
| 체크포인트 파일 | 2,048개 |
| 활성 연결 | 1,024개 |
| 해제 기록 | 2,048개 |
| 티켓 | 4,096개 |

저장에 성공하면 해당 세션의 보호되지 않은 체크포인트를 정리합니다.
보존 기준은 최근 20개와 30일 이내입니다.
활성 연결의 최근 체크포인트와 고정한 원본은 계속 보호합니다.
사용한 티켓이나 기한이 남은 티켓의 원본도 보호합니다.
다른 세션의 체크포인트는 지우지 않습니다.
판단할 수 없거나 읽을 수 없는 기록은 경고와 함께 남깁니다.
정리에 실패해도 성공한 저장을 취소하지 않습니다.
한도를 넘는 쓰기는 정리 전에 `CHAINING_LIMIT`로 거부합니다.
따라서 보호된 기록이 저장소를 채울 수 있습니다.
이번 버전은 보호된 기록을 자동으로 지우지 않습니다.
`chain doctor`에서 사용량과 한도를 볼 수 있습니다.
다른 `CROSS_SESSION_HOME`은 별도 환경이며 기존 연결이나 체크포인트를 옮기지 않습니다.
저장소를 읽을 수 없으면 체이닝만 중지하고 메시지 전달은 계속 제공합니다.
플러그인을 삭제해도 체크포인트는 남습니다.
`--purge-runtime`으로 확인된 메시지 파일을 지워도 체크포인트는 남습니다.

## 개인정보와 알려진 한계

인계나 체크포인트에 담길 대화에는 비밀 정보를 쓰지 않습니다.
같은 OS 계정은 로컬 체크포인트 파일을 읽을 수 있습니다.
복원 내용은 모델 입력으로 모델 제공자에게 전달될 수 있습니다.
플러그인은 체크포인트를 만들거나 요약하려고 외부 모델을 호출하지 않습니다.

- 체이닝은 한 세션 안의 판단력을 바꾸지 않습니다.
- 자동 기록만으로는 결정과 미완료 작업을 충분히 넘길 수 없습니다. 세션이 구조화 인계를 써야 합니다.
- 같은 컴퓨터 안에서만 동작합니다.
- hook이 신뢰받지 않으면 체크포인트를 저장하지 않습니다.
- 해제해도 이미 전달한 문맥은 지워지지 않습니다.
- 티켓은 첫 사용자를 소유자로 삼으며 상위 세션의 의도를 인증하지 않습니다.
- 인계 내용은 모델의 보고이며 독립 검증 결과가 아닙니다.

실행한 시험과 운영체제별 한계는 [검증 기록](VERIFICATION.ko.md)에서 볼 수 있습니다.
