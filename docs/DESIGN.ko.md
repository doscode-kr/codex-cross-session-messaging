# 설계

[English](DESIGN.md)

## 범위

플러그인은 같은 컴퓨터의 독립 Codex CLI 세션을 연결합니다.
Windows와 macOS는 같은 Node.js 구현을 사용합니다.
플러그인은 특정 프로젝트 작업 관리 체계를 요구하지 않습니다.

## 연결

요청은 다음 경로를 따릅니다.

`Codex 세션 → MCP 도구 → 로컬 브로커 → 바이트 프록시 → 공유 Codex 데몬 → 수신 세션`

브로커는 로컬 JSONL 기록도 작성합니다.
브로커는 `codex app-server daemon version`으로 실행 중인 데몬의 소켓을 읽습니다.
브로커는 `codex app-server proxy`로 해당 소켓에 연결합니다.
의존성 `ws`는 바이트 프록시에서 WebSocket 프레임을 처리합니다.
메시지를 전달할 때 별도 모델 실행기를 시작하지 않습니다.
공유 데몬이 자식 환경의 티켓을 받지 못하므로 `chain launch`는 실행을 거부합니다.

## 세션 체이닝

[세션 체이닝](CHAINING.ko.md)은 메시지 기록 옆에 별도 로컬 저장소를 둡니다.
MCP 도구는 기존 도구처럼 호출 정보와 실행 중인 세션을 확인합니다.
CLI와 hook 프로세스는 같은 쓰기 잠금을 사용합니다.
연결 정보는 소문자 전체 UUID로 특정 원본 체크포인트를 고정합니다.
체크포인트는 검증한 작업 상태를 복사합니다.
기존 작업 상태의 소유자와 추가 실행 정책은 바꾸지 않습니다.
자동 대화 기록과 Git 정보는 구조화 인계와 따로 담습니다.
복원한 내용은 현재 사용자 요청 안에서 검토할 신뢰하지 않는 데이터입니다.

실행 티켓의 소유자는 하나이며 최초 사용 기한은 10분입니다.
저장소에는 티켓의 해시만 넣습니다.
티켓 저장과 사용 검사는 구현했지만 CLI 전달 경로는 아직 지원하지 않습니다.
해제는 기대한 체인과 체크포인트를 비교한 뒤 해제 기록을 남깁니다.
다시 연결할 때는 정확한 해제 기록 ID가 필요합니다.
체이닝 오류가 메시지 전달을 막지는 않습니다.

## 즉시 전달

작업 중인 수신 세션은 현재 작업 ID를 지정한 `turn/steer`를 받습니다.
대기 중인 수신 세션은 `turn/start`를 받습니다.
구현은 전달 전에 수신 세션 상태를 읽습니다.
구현은 입력 수락 전에 발생한 특정 명시적 거부에만 한 번 재시도합니다.
구현은 시간 초과를 재시도하지 않습니다.
구현은 전달 실패 후 큐나 중단을 사용하지 않습니다.
구현은 수신 세션의 모델이나 권한을 덮어쓰지 않습니다.

동료 세션의 본문은 `untrusted` 추가 문맥입니다.
작업 입력에는 메시지 ID와 처리 안내가 포함됩니다.
작업 입력은 짧은 표시용 표제도 제공합니다.
텍스트 자리표시자를 지원하는 Codex 화면은 이 표제를 사용할 수 있습니다.
모델 입력에는 전체 안내가 남습니다.
발신 세션의 권한 정보는 설명용입니다.
발신 세션의 권한 정보는 수신 세션에 새 권한을 부여하지 않습니다.

## 세션 식별

MCP 호출은 Codex 세션 메타데이터로 호출 세션을 식별합니다.
메타데이터가 없으면 MCP 프로세스는 `CODEX_THREAD_ID`를 사용합니다.
두 방법 모두 식별 정보를 제공하지 못하면 호출은 실패합니다.
플러그인은 최근 세션이나 작업 폴더나 부모 PID로 호출 세션을 추측하지 않습니다.
수신 세션은 공유 데몬에 적재된 독립 루트 세션이어야 합니다.
하위 에이전트 세션은 수신 대상에서 제외합니다.

`SessionStart` 훅은 프로젝트 정보와 권한 정보를 기록합니다.
Git worktree는 공통 Git 폴더로 프로젝트를 구분합니다.
플러그인은 다른 프로젝트로의 메시지도 허용합니다.

## 브로커와 기록

각 메시지 폴더는 브로커 인스턴스와 로컬 포트를 선택합니다.
브로커는 기록을 열기 전에 포트를 확보합니다.
동시에 시작한 브로커가 포트 확보에 실패하면 기록을 작성하지 않아야 합니다.
임의 토큰과 폴더 인스턴스 식별값은 인스턴스 간 잘못된 요청을 막습니다.
브로커는 로컬 컴퓨터의 loopback 주소에서만 요청을 받습니다.
클라이언트는 응답 후 각 HTTP 연결을 닫습니다.
이 방식은 재시작한 브로커에 이전 연결을 재사용하는 문제를 막습니다.
이 방식은 연결 처리 작업을 추가합니다.
클라이언트는 응답이 유실된 요청을 재전송하지 않습니다.

브로커는 리더 변경과 메시지 기록을 순서대로 처리합니다.
브로커는 같은 직렬 처리 경로에서 상태를 확인합니다.
브로커는 같은 직렬 처리 경로에서 기록을 변경합니다.
브로커는 Codex 전달 응답을 기다리는 동안 해당 경로를 점유하지 않습니다.
브로커는 세션 목록도 해당 경로 밖에서 조회합니다.
동시에 들어온 요청은 진행 중인 데몬 목록 조회를 공유합니다.
각 요청은 직렬 처리 경로에서 세션 상태를 갱신합니다.
일반 요청은 리더 세션이 사라지면 리더 해제를 저널에 저장할 수 있습니다.
`list_idle_notifications`, `get_work_state`, `set_work_state`는 해당 리더 저널 갱신을 생략합니다.
이후 요청은 데몬을 다시 조회합니다.
브로커는 일정 시간 동안 상태를 캐시하지 않습니다.
호출 세션을 확인하려면 세션 목록 조회가 성공해야 합니다.
같은 수신 세션의 요청은 각 Codex 응답을 받을 때까지 전송 순서를 유지합니다.
한 수신 세션의 전달 응답이 느려도 다른 수신 세션으로의 전달을 막지 않습니다.
브로커는 전달 응답을 기다립니다.
브로커는 수신 세션의 작업 완료를 기다리지 않습니다.
수락된 전달도 이후 결과 답장이 필요할 수 있습니다.
브로커는 메시지 환경마다 리더를 하나만 허용합니다.
현재 리더만 역할을 해제하거나 넘길 수 있습니다.
기본 환경은 같은 Codex 사용자 설정을 사용하는 프로젝트 전체에서 공유합니다.

기록을 추가할 때마다 브로커는 디스크 동기화를 수행합니다.
기록 저장 모듈은 시작할 때 파일을 나누어 읽습니다.
기록 저장 모듈은 메시지 메타데이터를 메모리에 유지합니다.
본문이 필요하면 기록 파일의 해당 위치에서 읽습니다.
메시지 기록 조회는 요청한 개수만 선택한 뒤 본문을 읽습니다.
같은 메타데이터를 다시 기록할 때는 이벤트를 추가하지 않습니다.
기록 저장 모듈은 앞의 완성된 이벤트를 모두 검사한 뒤 미완성 마지막 줄을 제거합니다.
완성된 이벤트가 잘못됐으면 기록을 변경하지 않고 시작을 중단합니다.
저장된 전달 결과 없이 전송이 중단되면 결과는 `uncertain`이 됩니다.
JSONL 파일은 기록입니다.
JSONL 파일은 이후 전달을 위한 큐가 아닙니다.
원본 메시지는 자동으로 만료되지 않습니다.
저장된 데이터가 늘면 디스크와 메타데이터 메모리와 복구 작업량도 증가합니다.
저장 동작과 복구 제한은 [운영 안내](OPERATIONS.ko.md)를 확인하세요.

브로커는 종료 요청도 직렬 처리 경로에서 처리합니다.
저널이 정상이면 남은 대기 알림 신청은 `SUBSCRIPTIONS_ACTIVE`로 브로커 종료를 막습니다.
저널 읽기 또는 쓰기 오류가 기록되면 명시적 종료 요청은 해당 신청을 보존하고 종료를 허용합니다.
전달 응답을 기다리는 중이면 브로커는 `DELIVERIES_ACTIVE`로 종료를 거부합니다.
종료 요청을 수락한 뒤 브로커는 새 요청을 `BROKER_STOPPING`으로 거부합니다.
이 검사는 브로커가 기록을 닫기 전에 전달 기록을 보호합니다.
브로커는 진행 중인 세션 조회와 대기 확인과 전달이 끝난 뒤 자원을 닫습니다.
시작 중 기록 복구가 실패하면 브로커는 기록 파일과 수신 포트를 닫습니다.

## 작업 상태

선택적 작업 보고는 한도가 있는 별도 `work-state-v1.json` 파일을 사용합니다.
새 작업에는 서버가 ID를 생성한 고정 체크리스트 항목이 필요합니다.
시도 시작은 실행 전에 시도 번호를 저장합니다.
각 항목은 최초 시도 이후 최대 3회 재시도할 수 있습니다.
현재 실행 중인 시도에는 결과를 한 번만 기록합니다.
미완료 항목이 있으면 작업 교체와 전체 완료를 거부합니다.
버전 1 파일은 계속 읽을 수 있습니다.
쓰기 성공 시 같은 파일에 스키마 버전 2를 저장합니다.
API는 보고된 근거 필드를 검사합니다.
API는 근거의 진실성을 검증하지 않습니다.
각 갱신은 호출 세션의 리비전을 확인합니다.
갱신은 해당 파일을 원자적으로 교체합니다.
추가 실행 자격은 브로커 메모리에만 존재합니다.
재시작은 실행 자격 없이 요약만 복원합니다.
Stop hook은 고정 문구를 사용합니다.
활성화된 검사는 추가 실행을 최대 한 번 허용합니다.
전체 계약은 [작업 상태와 종료 한도](CONTINUATION.ko.md)를 확인하세요.

## 대기 알림

브로커는 신청된 세션을 약 1초마다 확인합니다.
브로커는 작업 중 상태에서 대기 상태로 바뀐 것을 확인한 뒤 알림을 한 번 보냅니다.
메시지 전달에 붙인 알림은 전달한 작업의 종료 상태도 확인합니다.
이 확인은 이전 대기 상태를 새 작업의 완료로 처리하는 것을 막습니다.
브로커는 직렬 상태 갱신 경로 밖에서 작업 기록을 조회합니다.
느린 작업 기록 조회는 다른 메시지나 알림 취소를 막지 않습니다.
같은 신청의 확인이 겹치면 진행 중인 조회를 공유합니다.
브로커는 발송 전에 현재 세션 상태와 같은 신청을 다시 확인합니다.
신청 취소나 종료가 발생하면 늦게 끝난 확인은 알림을 발송하지 않습니다.
브로커는 알림을 전달하기 전에 신청을 제거합니다.
브로커는 불확실한 알림을 자동 재전송하지 않습니다.
대상 세션이 대기 중일 때 신청하면 이후 작업 중 상태에서 대기 상태로 바뀔 때까지 기다립니다.
대기 알림은 작업 완료의 증거가 아닙니다.

## 데이터 경계

브로커는 메시지 본문과 세션 메타데이터를 로컬에 저장합니다.
브로커는 선택적 작업 요약도 로컬에 저장합니다.
Codex는 설정된 모델 제공자에게 동료 세션 문맥을 보낼 수 있습니다.
작업 상태 도구 결과도 모델 제공자 요청에 포함될 수 있습니다.
로컬 저장만으로 메시지 내용이 컴퓨터 안에 머문다고 판단할 수 없습니다.
개인정보 제한은 [보안 안내](../SECURITY.ko.md)를 확인하세요.
