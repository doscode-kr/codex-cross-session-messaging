# 플러그인 삭제

[English](UNINSTALL.md)

플러그인 파일과 마켓플레이스 등록과 메시지 데이터는 별도 항목입니다.
기본 삭제는 메시지 데이터를 유지합니다.
기본 삭제는 선택적 `work-state-v1.json` 작업 보고도 유지합니다.
[세션 체이닝](CHAINING.ko.md)의 체크포인트와 연결 정보는 `--purge-runtime`을 사용해도 유지합니다.
브로커가 저널 오류를 기록했으면 대기 알림 취소를 저장할 수 없습니다.
이 경우 사용자는 취소 단계를 생략합니다.
해당 오류 후 명시적인 브로커 종료는 대기 알림 신청과 저널 이벤트를 보존합니다.
처리 중인 전달은 계속 종료를 막습니다.
사용자는 아래의 데이터 정리를 명시적으로 선택하지 않으면 복구를 위해 저널을 보존합니다.
사용자는 브로커를 다시 시작하기 전에 저장 장치 문제를 해결합니다.
보존된 대기 알림 신청은 재시작 후 대기 상태 확인을 다시 수행할 수 있습니다.
사용자는 설치할 때 사용한 `CODEX_HOME`을 지정합니다.

## 기본 삭제

1. 사용자는 필요한 메시지 기록을 보관합니다.
2. 저널이 정상이면 사용자는 신청한 원래 세션에서 대기 알림을 취소합니다.
3. 사용자는 플러그인을 읽은 Codex 세션을 닫습니다.
4. 사용자는 외부 셸에서 메시지 브로커를 종료합니다.

   ```text
   node plugins/cross-session/src/cli.mjs broker-stop
   ```

5. 사용자는 삭제 계획을 확인합니다.

   ```text
   node scripts/uninstall.mjs --dry-run
   ```

6. 사용자는 플러그인과 전용 마켓플레이스를 삭제합니다.

   ```text
   node scripts/uninstall.mjs
   ```

7. 사용자는 새 Codex CLI 세션을 엽니다.
8. 사용자는 `codex plugin list --json`으로 목록을 확인합니다.

별도 Codex 설정에는 `node scripts/uninstall.mjs --home <폴더>`를 사용합니다.
사용자는 먼저 `--dry-run`을 추가하여 계획을 확인합니다.
PowerShell에서 옵션을 지정할 때는 직접 Node.js 명령을 사용합니다.
스크립트는 Codex 자체를 삭제하지 않습니다.
스크립트는 Codex 데몬을 재시작하지 않습니다.
`broker-stop`의 `BROKER_OFFLINE`은 해당 메시지 폴더의 브로커가 실행 중이 아니라는 뜻입니다.
후속 플러그인 호출을 막으려면 브로커 종료 전에 플러그인 세션을 닫습니다.
SessionEnd hook은 브로커를 시작하지 않습니다.
스크립트는 원본을 확인한 전용 마켓플레이스만 삭제합니다.
원본 목록에는 cross-session 플러그인만 있어야 합니다.
다른 설치된 플러그인이 마켓플레이스를 사용하면 스크립트는 등록을 유지합니다.
원본을 확인할 수 없으면 스크립트는 마켓플레이스를 유지합니다.
스크립트는 확인된 `.cross-session-install.json` 설치 기록을 삭제합니다.
확인되지 않은 플러그인 캐시가 있으면 스크립트는 멈춥니다.
안전하지 않은 연결 경로가 있으면 스크립트는 멈춥니다.

## 기본 메시지 데이터 삭제

경고: 데이터 정리는 저장된 메시지와 이름 등록과 작업 보고를 삭제합니다.
사용자는 삭제한 데이터를 플러그인에서 복구할 수 없습니다.

1. 사용자는 필요한 메시지 기록을 보관합니다.
2. 저널이 정상이면 사용자는 신청한 원래 세션에서 대기 알림을 취소합니다.
3. 사용자는 브로커를 시작할 수 있는 세션을 닫습니다.
4. 사용자는 외부 셸에서 `node plugins/cross-session/src/cli.mjs broker-stop`을 실행합니다.
5. 사용자는 데이터 정리 계획을 확인합니다.

   ```text
   node scripts/uninstall.mjs --purge-runtime --dry-run
   ```

6. 사용자는 대상 확인 후 데이터 정리를 실행합니다.

   ```text
   node scripts/uninstall.mjs --purge-runtime
   ```

정리는 표준 `<CODEX_HOME>/cross-session` 폴더의 확인된 제품 파일에만 적용됩니다.
정리 대상은 `events.jsonl`과 `auth-token`과 기존 `work-state-v1.json`입니다.
스크립트는 삭제 전에 작업 상태 파일의 형식과 크기를 검사합니다.
작업 상태 파일이 유효하지 않으면 스크립트는 플러그인 삭제 전에 정리를 중단합니다.
사용자는 해당 파일을 수동 확인을 위해 유지합니다.
정리는 다른 파일을 유지합니다.
정리는 Codex 설정 폴더 전체를 삭제하지 않습니다.
정리는 사용자 지정 `CROSS_SESSION_HOME` 폴더를 자동 삭제하지 않습니다.
브로커가 실행 중이면 정리는 오류로 멈춥니다.
스크립트는 데이터 삭제 직전에 브로커를 다시 확인합니다.
이 확인이 실패하면 플러그인 삭제 후에도 메시지 데이터가 남을 수 있습니다.
모의 실행은 브로커 실행 여부를 검사하지 않습니다.
사용자는 실행 중인 브로커의 기록이나 인증 토큰을 삭제하지 않습니다.

Windows의 자동 정리는 메시지 폴더의 8.3 짧은 경로도 확인합니다.
짧은 경로가 운영체제의 전체 경로와 다르면 정리는 삭제를 거부합니다.
짧은 경로를 확인할 수 없어도 정리는 삭제를 거부합니다.
기존 브로커는 같은 폴더의 짧은 경로를 기준으로 다른 포트를 사용할 수 있습니다.
전체 경로의 포트가 중지되어도 짧은 경로의 브로커 종료를 확인한 것은 아닙니다.
이 경로 검사는 `--purge-runtime`과 해당 모의 실행에 적용됩니다.
첫 검사는 플러그인 삭제 전에 실행됩니다.
첫 검사가 실패하면 명령은 플러그인과 메시지 데이터를 모두 유지합니다.
사용자는 데이터를 유지하며 플러그인을 삭제하려면 `--purge-runtime` 없이 기본 삭제를 실행합니다.
사용자는 기본 삭제에 전체 `CODEX_HOME` 폴더 경로를 지정합니다.
사용자는 `--home`에 8.3 짧은 경로를 지정하지 않습니다.
사용자는 관련 브로커의 종료를 모두 확인한 후 아래의 수동 데이터 삭제 절차를 따릅니다.

브로커 종료 명령은 `node plugins/cross-session/src/cli.mjs broker-stop`입니다.
저널이 정상이고 대기 알림 신청이 남으면 브로커는 종료를 거부합니다.
이 경우 사용자는 신청한 원래 세션에서 대기 알림을 취소합니다.
브로커가 저널 오류를 기록했으면 명시적인 종료는 대기 알림 신청을 보존하고 종료를 허용합니다.
이 종료는 대기 알림 신청을 취소하지 않습니다.
이 종료는 저널 이벤트를 삭제하지 않습니다.
처리 중인 전달은 계속 종료를 막습니다.
저널이 정상이고 다른 세션이 신청했으면 사용자는 해당 세션에 취소를 요청합니다.
다음 플러그인 호출은 브로커를 다시 시작할 수 있습니다.
사용자는 정리를 다시 실행하기 전에 플러그인 세션을 닫습니다.

사용자 지정 데이터 폴더는 사용자가 해석된 절대 경로를 먼저 확인합니다.
사용자는 해당 폴더를 사용하는 세션을 먼저 종료합니다.
사용자는 필요한 기록을 보관한 후 제품 파일을 직접 삭제합니다.
사용자는 사용자 지정 폴더의 다른 파일을 삭제하지 않습니다.

## 직접 플러그인 삭제

원본 저장소 이동 후 플러그인 목록 조회가 실패하면 사용자는 먼저 원래 원본 경로를 복원합니다.
사용자는 [원본 복구 절차](OPERATIONS.ko.md#사용할-수-없는-원본-폴더-복구)를 따릅니다.
삭제 스크립트는 플러그인 목록 없이 안전하게 진행할 수 없습니다.
설치 기록은 해당 목록을 대신하지 않습니다.
설치 기록은 등록 삭제를 허용하지 않습니다.
모의 실행은 해당 목록을 조회하지 않습니다.

1. 사용자는 `codex plugin list --json`으로 설치 목록을 읽습니다.
2. 사용자는 다른 설치된 플러그인의 `cross-session-local` 사용 여부를 확인합니다.
3. 저널이 정상이면 사용자는 신청한 원래 세션에서 대기 알림을 취소합니다.
4. 사용자는 플러그인을 읽은 세션을 닫습니다.
5. 사용자는 외부 셸에서 `node plugins/cross-session/src/cli.mjs broker-stop`을 실행합니다.
6. 사용자는 `codex plugin remove cross-session@cross-session-local`을 실행합니다.
7. 다른 설치된 플러그인이 사용하지 않으면 사용자는 `codex plugin marketplace remove cross-session-local`을 실행합니다.
8. 사용자는 새 Codex CLI 세션을 엽니다.
9. 사용자는 `codex plugin list --json`을 실행합니다.

이 Codex 명령은 플러그인 캐시와 마켓플레이스 등록을 삭제합니다.
이 명령은 메시지 폴더를 삭제하지 않습니다.
다른 설치된 플러그인이 사용하면 사용자는 마켓플레이스 등록을 유지합니다.
사용자는 확인을 마칠 때까지 원본 저장소를 유지합니다.
사용자는 삭제를 마친 후 원본 저장소를 별도 파일 작업으로 삭제할 수 있습니다.

## Windows 경로 별칭 거부 후 수동 데이터 삭제

경고: 수동 데이터 삭제는 저장된 메시지와 이름 등록과 작업 보고를 영구 삭제합니다.

1. 사용자는 메시지 폴더에서 필요한 기록을 보관합니다.
2. 저널이 정상이면 사용자는 신청한 원래 세션에서 대기 알림을 취소합니다.
3. 사용자는 관련 Codex 세션을 모두 닫습니다.
4. 사용자는 외부 셸에서 전체 경로나 짧은 경로를 사용한 각 브로커를 종료합니다.
5. 사용자는 운영체제의 프로세스 도구로 해당 브로커 프로세스의 종료를 모두 확인합니다.
6. 플러그인이 남아 있으면 사용자는 `node scripts/uninstall.mjs --home <전체-설정-경로>`를 실행합니다.
7. 사용자는 메시지 폴더의 해석된 전체 경로를 확인합니다.
8. 사용자는 `events.jsonl`과 `auth-token`이 이 플러그인의 파일인지 확인합니다.
9. 사용자는 해당 폴더의 `events.jsonl`만 삭제합니다.
10. 사용자는 해당 폴더의 `auth-token`만 삭제합니다.
11. `work-state-v1.json`이 있으면 사용자는 이 플러그인의 파일인지 확인합니다.
12. 사용자는 확인한 작업 상태 파일만 삭제합니다.
13. 메시지 폴더가 비었으면 사용자는 해당 폴더를 삭제합니다.

사용자는 각 브로커가 사용한 메시지 환경에서 `node plugins/cross-session/src/cli.mjs broker-stop`을 실행합니다.
필요하면 사용자는 `CROSS_SESSION_HOME`에 해당 브로커가 사용한 경로 표기를 지정합니다.
사용자는 종료 명령 후 환경 설정을 복원합니다.
서로 다른 포트를 사용하는 브로커들이 같은 폴더의 인증 토큰을 공유할 수 있습니다.
한 경로의 `BROKER_OFFLINE`만으로 모든 브로커의 종료를 확인할 수 없습니다.
관련 브로커의 종료를 모두 확인할 수 없으면 사용자는 데이터 파일을 유지합니다.
사용자는 다른 파일과 상위 Codex 설정 폴더를 유지합니다.
이 절차는 Codex 데몬 재시작이 필요하지 않습니다.
