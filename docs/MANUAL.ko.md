# 사용자 설명서

[English](MANUAL.md) · [문서 목록](README.ko.md) · [프로젝트 소개](../README.ko.md)

Cross Session은 같은 컴퓨터의 독립 Codex CLI 세션 사이에 메시지를 보냅니다.
이 설명서는 설치와 일상 사용을 안내합니다.
플러그인은 특정 작업 관리 절차를 요구하지 않습니다.
브로커는 메시지 전달을 처리하는 로컬 프로그램입니다.
브로커는 메시지도 기록합니다.

## 1. 준비와 설치

사용자는 Node.js 20 이상이 필요합니다.
사용자는 플러그인과 공유 데몬을 지원하는 Codex CLI가 필요합니다.
기록된 CI 검증은 Windows와 macOS의 Node.js 20과 22에서 Codex CLI 0.161.0을 사용했습니다.
검증 기록은 검사한 commit과 해당 결과를 명시합니다.
이전 Windows 기록에는 Codex 0.159.3 공유 데몬도 포함됩니다.
해당 기록은 다른 Codex 버전을 검증하지 않았습니다.
플러그인은 Codex의 `experimentalApi` 기능을 사용합니다.
통신 규약이 바뀌면 세션 조회나 전달이 실패할 수 있습니다.
운영체제별 근거는 [검증 한계](VERIFICATION.ko.md)를 확인하세요.

이 릴리스는 실험판입니다.
사용자는 직접 확인하면서 로컬 협업에 사용합니다.
전달 수락은 모델의 이해를 보장하지 않습니다.
전달 수락은 작업 완료를 보장하지 않습니다.

1. 사용자는 원본 저장소를 복제합니다.

   ```text
   git clone https://github.com/doscode-kr/codex-cross-session-messaging.git
   ```

2. 사용자는 원본 폴더로 이동합니다.

   ```text
   cd codex-cross-session-messaging
   ```

3. 사용자는 설치 계획을 확인합니다.

   ```text
   node scripts/install.mjs --dry-run
   ```

4. 사용자는 플러그인을 설치합니다.

   ```text
   npm run install:global
   ```

5. 사용자는 새 Codex CLI 세션을 엽니다.
6. 사용자는 `/hooks`에서 플러그인 훅을 검토합니다.
7. 사용자는 검토한 훅을 신뢰하도록 설정합니다.

설치 스크립트는 Codex 설정에 `cross-session-local`을 등록합니다.
설치 스크립트는 `cross-session@cross-session-local`을 설치합니다.
설치 스크립트는 훅 신뢰를 승인하지 않습니다.
사용자는 업데이트와 삭제를 위해 원본 폴더를 유지합니다.
사용자는 PowerShell에서 옵션을 지정할 때 직접 Node.js 명령을 사용합니다.

## 2. 두 세션 등록

예제는 `alpha`와 `beta`라는 이름을 사용합니다.
사용자는 같은 컴퓨터의 서로 다른 터미널에서 각 세션을 엽니다.
두 세션은 같은 Codex 설정 폴더와 메시지 설정을 사용합니다.
사용자는 두 세션에 `--no-daemon`을 지정하지 않습니다.

1. 사용자는 `alpha` 세션을 엽니다.
2. 사용자는 `alpha`에 다음 요청을 입력합니다.

   ```text
   $cross-session
   현재 세션 이름을 alpha로 등록해 주세요.
   ```

3. 사용자는 `beta` 세션을 엽니다.
4. 사용자는 `beta`에 다음 요청을 입력합니다.

   ```text
   $cross-session
   현재 세션 이름을 beta로 등록해 주세요.
   사용할 수 있는 세션 목록을 보여 주세요.
   ```

목록에는 적재된 독립 세션 두 개가 보여야 합니다.
실행 중인 세션은 서로 다른 이름을 사용합니다.
`leader`는 예약된 이름입니다.
이름이 불명확하면 사용자는 정확한 세션 ID를 사용합니다.
목록은 같은 프로젝트의 세션을 먼저 표시합니다.
사용자는 같은 컴퓨터의 다른 프로젝트에도 메시지를 보낼 수 있습니다.
플러그인은 하위 subagent 세션을 제외합니다.

## 3. 리더 지정

리더는 선택 사항입니다.
사용자만 리더 역할을 지정할 수 있습니다.
같은 컴퓨터의 기본 메시지 환경에는 리더가 하나만 존재합니다.
같은 메시지 환경의 여러 프로젝트는 해당 리더를 공유합니다.
리더 역할은 파일 권한이나 도구 권한을 추가하지 않습니다.

1. 사용자는 `alpha`에 다음 요청을 입력합니다.

   ```text
   현재 세션을 cross-session 리더로 지정합니다.
   ```

2. 사용자는 `beta`에 세션 목록을 요청합니다.
3. 사용자는 `alpha`의 리더 역할을 확인합니다.

기존 리더가 있으면 `claim_leader`는 실패합니다.
현재 리더는 `transfer_leader`나 `release_leader`를 사용할 수 있습니다.
리더 세션이 공유 데몬에서 사라지면 브로커는 역할을 해제합니다.
브로커는 후임 리더를 자동 지정하지 않습니다.

## 4. 메시지 전송과 답장

1. 사용자는 `beta`에 다음 요청을 입력합니다.

   ```text
   alpha에게 다음 메시지를 보내 주세요: 현재 작업과 남은 작업을 보고해 주세요.
   ```

2. 사용자는 반환된 `messageId`를 기록합니다.
3. 사용자는 `alpha`에서 요청을 읽습니다.
4. 사용자는 `alpha`에 결과 답장을 요청합니다.

   ```text
   MESSAGE_ID의 발신 세션에 현재 작업과 남은 작업을 답장해 주세요.
   ```

사용자는 `MESSAGE_ID`를 기록한 메시지 ID로 바꿉니다.
사용자가 리더를 지정한 후에는 `to: "leader"`를 사용할 수 있습니다.
사용자는 자기 세션에 메시지를 보내지 않습니다.
`reply`는 현재 세션이 받은 메시지의 발신 세션을 사용합니다.
`reply`는 관련 없는 수신 세션을 선택하지 않습니다.

| 수신 세션 | 전달 방식 |
|---|---|
| 작업 중 | `turn/steer`가 현재 작업에 입력을 추가합니다. |
| 대기 중 | `turn/start`가 새 작업을 시작합니다. |
| 직접 입력 불가 | 전달이 오류를 반환합니다. |

긴 도구 호출은 메시지 처리를 늦출 수 있습니다.
플러그인은 전달 실패를 완료 큐나 중단으로 바꾸지 않습니다.
동료 세션의 메시지는 사용자 지시나 승인이 아닙니다.
수신 세션은 사용자의 작업 범위를 유지합니다.
수신 세션은 자체 권한을 유지합니다.
메시지는 동시 파일 수정 충돌을 막지 않습니다.

### 다른 세션과 직접 작업 협의

모든 세션은 다른 세션에 질문을 보낼 수 있습니다.
모든 세션은 작업 방법을 협의할 수 있습니다.
모든 세션은 다른 세션에 답장할 수 있습니다.
이 통신에는 리더 역할이 필요하지 않습니다.
사용자가 리더를 지정하면 동료 세션은 협의 결과를 해당 리더에게 보고할 수 있습니다.
이 예제에서 사용자는 세 번째 세션을 `gamma`로 등록합니다.
각 세션은 사용자에게 승인받은 작업 범위를 유지합니다.

1. 사용자는 `beta`에 공동 API 변경에 관한 질문을 `gamma`로 보내도록 요청합니다.
2. 사용자는 `gamma`에 해당 메시지로 관련 파일과 변경안을 답장하도록 요청합니다.
3. 사용자는 `beta`에 결정이나 남은 질문을 답장하도록 요청합니다.
4. 사용자가 `alpha`를 리더로 지정했다면 사용자는 `beta`에 결과를 `alpha`로 보고하도록 요청합니다.

세션은 처음 질문과 다른 수신 세션으로 보내는 보고에 `send_message`를 사용합니다.
세션은 협의 답장에 수신한 메시지 ID와 `reply`를 사용합니다.
보고에는 결정과 관련 파일과 근거와 남은 질문을 포함할 수 있습니다.
동료 세션의 합의는 사용자 승인이 아닙니다.
동료 세션의 합의는 어느 세션의 권한도 확대하지 않습니다.
동료 세션의 합의는 어느 세션의 작업 범위도 확대하지 않습니다.
예정한 파일 변경이 겹치면 세션은 계속 작업하기 전에 해당 변경을 협의합니다.
세션은 해결하지 못한 충돌을 지정된 리더에게 보고합니다.
메시지는 파일을 잠그지 않습니다.
메시지는 특정 작업 관리 절차를 요구하지 않습니다.

## 5. 전달과 읽음과 완료 확인

| 결과 | 의미 |
|---|---|
| `accepted` | Codex가 입력을 수락했습니다. 읽음과 완료는 확인되지 않았습니다. |
| `failed` | 전달이 실패했습니다. 사용자는 재시도 전에 오류를 읽습니다. |
| `uncertain` | 전달 결과를 알 수 없습니다. 사용자는 자동 재전송하지 않습니다. |
| `acknowledgedAt` | 수신 세션이 읽음을 기록했습니다. 이 기록은 작업 완료를 증명하지 않습니다. |
| 결과 답장 | 수신 세션이 작업을 보고합니다. 사용자는 보고된 근거를 확인합니다. |

플러그인은 자동 작업 완료 상태를 제공하지 않습니다.
전송 응답에는 `taskCompleted: false`가 포함됩니다.
읽음 확인 결과에도 `taskCompleted: false`가 포함됩니다.

1. 사용자는 현재 세션에 기록한 메시지 ID의 `get_message` 호출을 요청합니다.
2. 사용자는 저장된 전달 상태를 확인합니다.
3. 사용자는 완료 근거를 위해 수신 세션의 결과 답장을 읽습니다.

전송 응답을 잃으면 사용자는 발신 기록을 먼저 읽습니다.
사용자는 `read_messages`에 `direction: "outbox"`와 `detail: true`를 지정합니다.
사용자는 재전송을 검토하기 전에 저장된 메시지 ID를 찾습니다.
전달이 불확실하면 사용자는 사용할 수 있는 연락 방법으로 수신 세션의 상황을 확인합니다.
사용자는 답장 누락을 전달 실패로 판단하지 않습니다.

발신 세션에 읽음 확인이 필요할 때만 사용자는 `acknowledge`를 사용합니다.
수신 세션만 메시지의 읽음을 확인할 수 있습니다.
이 도구는 동료 이벤트를 보내지 않고 읽음을 기록합니다.
세션은 유용한 결과와 필요한 질문과 작업을 막는 오류에 답장합니다.
세션은 수신 확인만 담은 답장을 피합니다.
세션은 수신 확인만 담은 답장에 다시 답장하지 않습니다.

## 6. 대기 알림 신청과 취소

1. 사용자는 `beta`에 다음 요청을 입력합니다.

   ```text
   alpha가 다음에 대기 상태가 되면 한 번 알려 주세요.
   notify_when_idle을 사용하고 subscriptionId를 보여 주세요.
   ```

2. 사용자는 반환된 `subscriptionId`를 기록합니다.
3. 사용자는 취소가 필요하면 `beta`에서 해당 ID를 사용합니다.

   ```text
   대기 알림 SUBSCRIPTION_ID를 취소해 주세요.
   ```

사용자는 `SUBSCRIPTION_ID`를 기록한 신청 ID로 바꿉니다.
신청한 세션만 해당 알림을 취소할 수 있습니다.
알림은 확인한 작업 중 → 대기 상태 변경 후 한 번 전달됩니다.
`alpha`가 이미 대기 중이면 알림은 이후 상태 변경을 기다립니다.
브로커는 약 1초마다 상태를 확인합니다.
브로커는 짧은 상태 변경을 놓칠 수 있습니다.
대기 알림은 작업 완료를 증명하지 않습니다.
브로커는 전달이 불확실한 알림을 자동 재전송하지 않습니다.

`send_message`에도 `notify_when_idle: true`를 지정할 수 있습니다.
해당 전송 응답은 신청 ID를 반환하지 않습니다.
취소용 ID가 필요하면 사용자는 별도 `notify_when_idle`을 호출합니다.

## 7. 짧은 출력과 상세 출력

MCP 결과는 기본으로 짧은 문장을 표시합니다.
전체 데이터는 `structuredContent`에 유지됩니다.
메시지 요약은 본문 미리보기를 포함합니다.
요약은 저장된 메시지 본문을 줄이지 않습니다.

1. 사용자는 현재 세션에 저장된 메시지의 전체 본문을 요청합니다.

   ```text
   get_message에 message_id MESSAGE_ID와 detail true를 지정해 주세요.
   ```

2. 사용자는 전체 JSON이 필요하면 다른 도구에도 `detail: true`를 요청합니다.

Codex는 도구 결과와 추가 문맥의 화면 표시를 제어합니다.
플러그인은 동료 알림에 `동료 세션 알림 / Peer message`라는 짧은 UI 표제를 제공합니다.
Codex CLI 0.161.0은 작업 중 전달과 대기 중 전달에서 `text_elements`로 해당 표제를 수락하고 저장합니다.
모델은 동료 메시지와 사용자 지시를 구분하는 안내를 계속 받습니다.
모델은 동료 메시지와 사용자 승인을 구분하는 안내를 계속 받습니다.
전체 메시지는 신뢰하지 않는 추가 문맥에 남습니다.
표제는 권한을 변경하지 않습니다.
표제는 작업 범위를 변경하지 않습니다.
일부 호스트는 표제 대신 원래 알림을 표시할 수 있습니다.
Codex는 짧은 결과 문장과 함께 전체 구조화 데이터나 동료 문맥을 표시할 수 있습니다.
플러그인은 화면의 메시지 수 감소를 보장하지 않습니다.
플러그인은 모델의 모든 답장 왕복을 막을 수 없습니다.
확인한 입력 스키마에는 모든 호스트에서 알림과 문맥을 숨기는 옵션이 없습니다.
`detail`은 결과 문장만 변경합니다.
`detail`은 전달과 저장 데이터와 권한을 변경하지 않습니다.

## 8. 메시지 환경 설정

| 설정 | 기능 |
|---|---|
| 기본값 | 데이터는 `~/.codex/cross-session/`에 있습니다. |
| `CODEX_HOME` | 데이터는 `<CODEX_HOME>/cross-session/`에 있습니다. |
| `CROSS_SESSION_HOME` | 데이터는 지정한 폴더에 있습니다. |
| `CROSS_SESSION_CODEX_BIN` | Codex 실행 파일이나 JavaScript 진입 파일의 절대 경로를 사용합니다. |

사용자는 세션을 열기 전에 환경변수를 설정합니다.
이름과 리더를 공유하는 세션은 같은 설정을 사용합니다.
별도 메시지 폴더는 별도 이름 등록과 리더 상태를 사용합니다.
Windows에서는 사용자가 전체 경로를 사용합니다.
Windows에서는 사용자가 기본 `codex.exe`를 우선 사용합니다.
`CROSS_SESSION_CODEX_BIN`에는 `.cmd`, `.bat`, `.ps1` 경로를 지정할 수 없습니다.
플러그인은 운영 중인 Codex 데몬을 재시작하지 않습니다.

기록은 메시지 본문과 세션 정보를 평문으로 저장합니다.
Codex는 설정된 모델 제공자에게 동료 문맥을 보낼 수 있습니다.
사용자는 로그 공유 전에 [보안과 개인정보 안내](../SECURITY.ko.md)를 읽습니다.

## 9. 플러그인 업데이트

1. 사용자는 현재 릴리스나 commit을 기록합니다.
2. 사용자는 등록된 원본 폴더에서 새 릴리스를 받습니다.
3. 사용자는 [변경 기록](../CHANGELOG.ko.md)을 읽습니다.
4. 사용자는 신청한 원래 세션에서 남은 대기 알림을 취소합니다.
5. 사용자는 기존 플러그인을 읽은 세션을 닫습니다.
6. 사용자는 외부 셸에서 브로커를 종료합니다.

   ```text
   node plugins/cross-session/src/cli.mjs broker-stop
   ```

7. 사용자는 `node scripts/install.mjs --dry-run`으로 설치 계획을 확인합니다.
8. 사용자는 설치된 플러그인 캐시를 삭제합니다.

   ```text
   codex plugin remove cross-session@cross-session-local
   ```

9. 사용자는 `npm run install:global`로 새 원본을 설치합니다.
10. 사용자는 새 Codex CLI 세션을 엽니다.
11. 사용자는 `/hooks`에서 새 훅을 검토합니다.

이 절차는 메시지 데이터를 유지합니다.
세션을 먼저 닫으면 종료 훅의 브로커 재시작을 방지합니다.
원본 파일 변경만으로 설치된 캐시의 업데이트를 확인할 수 없습니다.
원본 폴더가 바뀌면 사용자는 [운영 안내](OPERATIONS.ko.md)를 따릅니다.
다른 플러그인이 사용하면 사용자는 공유 마켓플레이스 등록을 유지합니다.

## 10. 플러그인 삭제

기본 삭제는 저장된 메시지 데이터를 유지합니다.
사용자는 설치할 때 사용한 Codex 설정 폴더를 지정합니다.

1. 사용자는 필요한 메시지 기록을 보관합니다.
2. 사용자는 신청한 원래 세션에서 남은 대기 알림을 취소합니다.
3. 사용자는 플러그인을 읽은 세션을 닫습니다.
4. 사용자는 외부 셸에서 `node plugins/cross-session/src/cli.mjs broker-stop`을 실행합니다.
5. 사용자는 `node scripts/uninstall.mjs --dry-run`으로 삭제 계획을 확인합니다.
6. 사용자는 `node scripts/uninstall.mjs`로 플러그인을 삭제합니다.
7. 사용자는 `codex plugin list --json`으로 결과를 확인합니다.

별도 Codex 설정 폴더에는 사용자가 `--home <전체-설정-경로>`를 지정합니다.
다른 설치된 플러그인이 사용하지 않으면 스크립트는 확인한 전용 마켓플레이스를 삭제합니다.
스크립트는 Codex를 삭제하지 않습니다.
스크립트는 Codex 데몬을 재시작하지 않습니다.

경고: `--purge-runtime`은 확인된 메시지 기록 파일을 영구 삭제합니다.
사용자는 이 옵션을 사용하기 전에 [데이터 삭제 절차](UNINSTALL.ko.md)를 읽습니다.
모의 실행은 경로의 안전성을 검사합니다.
모의 실행은 브로커의 실행 여부를 검사하지 않습니다.
Windows의 8.3 별칭이나 별칭 확인 실패는 자동 데이터 정리를 막습니다.
처음 데이터 정리를 거부하면 스크립트는 플러그인과 데이터를 유지합니다.
이후 검사를 거부하면 플러그인만 삭제될 수 있습니다.
사용자 지정 `CROSS_SESSION_HOME` 폴더는 자동 삭제하지 않습니다.
한 경로의 `BROKER_OFFLINE` 결과는 모든 별칭 브로커의 종료를 증명하지 않습니다.
삭제 안내는 Windows의 수동 절차를 제공합니다.

## 11. 오류 해결

| 오류나 상태 | 조치 |
|---|---|
| `NAME_IN_USE` | 사용자는 `leader` 이외의 고유 이름을 선택합니다. |
| `RECIPIENT_NOT_FOUND`나 `AMBIGUOUS_RECIPIENT` | 사용자는 `list_agents`에서 정확한 실행 중 세션 ID를 선택합니다. |
| `LEADER_EXISTS` | 사용자 지정 후 현재 리더에게 역할 이전이나 해제를 요청합니다. |
| `NO_LEADER` | 사용자는 리더를 지정하거나 정확한 수신 세션 ID를 사용합니다. |
| `IDENTITY_MISSING` | 사용자는 지원하는 Codex CLI로 세션을 엽니다. 호출자 ID를 추측하지 않습니다. |
| `DAEMON_REQUIRED` | 사용자는 공유 데몬을 사용하는 일반 CLI 세션을 엽니다. |
| `DELIVERY_FAILED` | 사용자는 재시도 전에 저장된 오류와 수신 상태를 읽습니다. |
| `DELIVERY_UNCERTAIN` | 사용자는 재전송 전에 발신 기록과 수신 세션의 상황을 확인합니다. |
| `MESSAGE_NOT_FOUND` | 사용자는 현재 세션이 주고받은 메시지를 지정합니다. |
| `SUBSCRIPTIONS_ACTIVE` | 사용자는 브로커 종료 전에 남은 대기 알림을 취소합니다. |
| 종료 중 `BROKER_OFFLINE` | 사용자는 지정한 메시지 환경과 경로 별칭을 확인합니다. |
| 마켓플레이스 원본 충돌 | 사용자는 운영 안내의 원본 변경 절차를 따릅니다. |
| Windows 경로 별칭 거부 | 사용자는 삭제 안내의 전체 경로와 수동 정리 절차를 따릅니다. |

1. 사용자는 `npm run doctor`로 데몬과 세션 목록을 확인합니다.
2. 사용자는 출력에서 개인 경로와 세션 정보를 제거합니다.
3. 사용자는 운영체제와 Node.js와 Codex와 플러그인 버전을 포함하여 오류를 보고합니다.

오류는 [이슈 목록](https://github.com/doscode-kr/codex-cross-session-messaging/issues)에 보고합니다.
취약점은 [보안 신고 안내](../SECURITY.ko.md)를 따릅니다.
사용자는 공개 보고에 토큰이나 비공개 메시지 본문을 포함하지 않습니다.

## 12. 도구 인자 참조

아래 예제는 MCP 도구 인자입니다.
아래 예제는 셸 명령이 아닙니다.
사용자는 `MESSAGE_ID`와 `SUBSCRIPTION_ID`를 반환된 실제 ID로 바꿉니다.
예제는 등록된 이름으로 `alpha`나 `beta`를 선택합니다.
호출 세션은 Codex 메타데이터로 확인합니다.

| 도구 | 예제 인자 |
|---|---|
| `list_agents` | `{}` |
| `register_session` | `{"name":"alpha"}` |
| `claim_leader` | `{}` |
| `send_message` | `{"to":"alpha","message":"남은 작업을 보고해 주세요."}` |
| `reply` | `{"message_id":"MESSAGE_ID","message":"확인을 마쳤습니다. 근거: ..."}` |
| `read_messages` | `{"direction":"inbox","limit":20,"unacknowledged_only":true,"detail":true}` |
| `get_message` | `{"message_id":"MESSAGE_ID","detail":true}` |
| `acknowledge` | `{"message_id":"MESSAGE_ID"}` |
| `notify_when_idle` | `{"to":"alpha"}` |
| `cancel_idle_notification` | `{"subscription_id":"SUBSCRIPTION_ID"}` |
| `transfer_leader` | `{"to":"beta"}` |
| `release_leader` | `{}` |

사용자가 지정한 리더만 역할을 이전하거나 해제할 수 있습니다.
모든 MCP 도구는 boolean `detail` 옵션을 받습니다.
`read_messages`의 `direction`은 `inbox`, `outbox`, `both`를 받습니다.
`limit`은 1부터 100까지입니다.
`limit`의 기본값은 20입니다.
`send_message`는 수신 세션의 메시지에 답장할 때 선택 인자 `reply_to`를 받습니다.

셸 CLI는 도구 이름과 `--message-id` 같은 옵션을 받습니다.
사용자는 `--session`에 정확한 세션 ID를 지정하거나 기존 `CODEX_THREAD_ID`를 사용합니다.
CLI는 `--detail` 없이도 전체 JSON을 출력합니다.
CLI의 `--detail`은 별도 값을 받지 않습니다.
CLI는 `--detail`을 브로커로 보내지 않습니다.
일반 세션 통신에는 사용자가 Codex 안의 MCP 도구를 사용합니다.
